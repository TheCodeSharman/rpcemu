# CLAUDE.md

This file guides Claude Code (claude.ai/code) when working in this
repository.  It lives on the `base` branch (see below), so it is present on
every feature branch and still cancels out of the patches we send upstream.

## What this is

A customised git fork of **RPCEmu**, the Acorn Risc PC / A7000 emulator.
Upstream RPCEmu is **Mercurial** at marutan.net and we can't push back, so
this fork keeps our patches as git branches and we send them to marutan as
unified diffs.  The RiscPc "raster-lab" project consumes this fork
(`setup-rpcemu.sh` clones it).

## Branch model

We don't control upstream, so the branch model is built around producing
**clean upstream-submission diffs** while still giving consumers one
predictable branch.

- **`upstream`** — **PRISTINE RPCEmu, nothing else.**  It is the verbatim
  import, tagged with the release version (`v0.9.5`, `v0.9.6`, ...);
  `git diff v0.9.5 upstream` is empty.  Nothing of ours lives here — it's a
  bare mirror, so importing a new release is a clean overwrite.
- **`base`** — **`upstream` + one commit of dev/build infra**: `.gitignore`,
  `Makefile`, `devenv.{nix,lock,yaml}`, `.envrc`, `CLAUDE.md`, and the
  untracking of the runtime `cmos.ram`/`rpc.cfg`.
  This is the branch we actually *develop* on; feature branches sit on it so
  they inherit the build/dev environment (Makefile, devenv, …).  **`base` moving
  costs a restack of every feature**, so keep churn off it — that is why the
  re-integration recipe lives on `meta`, not here.
- **`meta`** — an **orphan** branch (no shared history with the source) holding
  the re-integration recipe: `tools/reintegrate.sh` and its `FEATURES` list.
  It sits here precisely *because* adding or reordering a feature must not touch
  `base`: editing `FEATURES` is one commit on `meta`, and no feature branch has
  to move.  Nothing builds from `meta`; it is not part of any patch.
- **`integration`** — the **derived** branch (the repo's **default**).  It is
  `base` + one **squashed** commit per feature branch, regenerated by
  `meta`'s `reintegrate.sh` — never hand-edited.  What `setup-rpcemu.sh` clones.
- **`feature/*`** — **long-lived patch branches off `base`**.  Each carries one
  logical patch; `integration` picks them up via re-integration.  Big install
  tooling (setup-install.sh + the boot-build tree) lives on
  **`feature/build-tooling`**, kept off `base` so it's not on every branch.

The submission diff for any patch is **`git diff base feature/X`** — the infra
is on both sides, so it cancels out and the diff is pure RPCEmu source, ready to
email to marutan.  (`upstream` stays pristine and is NOT what you diff against.)

**Restacking:** `git-branchless` is in the devenv — after `base`/`upstream` moves,
`git restack` re-applies the feature branches onto it; `git sl` shows the whole
quilt.  Run git under `direnv exec /home/msharman/Projects/rpcemu …` (or an
interactive repo shell) so the branchless hooks find the binary.

### Re-integrating

`integration` is **rebuilt, not accumulated**.  The script lives on the `meta`
branch, so run it straight from there — there is nothing to check out:

```sh
git show meta:tools/reintegrate.sh | bash
```

It does `git checkout -B integration base`, then `git merge --squash` + commit
for each feature in its `FEATURES` list, collapsing each branch to one
commit.  Review, then `git push --force-with-lease origin integration`.
Re-run any time a feature changes; add/remove a feature with **one commit on
`meta`** — `base` and the feature branches never move for it.  `git rerere` is enabled, so a cross-feature conflict is
resolved once and replayed on later rebuilds.

### Importing a new upstream release

1. On `upstream`: rsync the new RPCEmu source over the tree (from a sidecar hg
   clone in `~/opt/rpcemu-upstream/`), commit as `Import RPCEmu x.y.z`, tag
   `vx.y.z`, force-push `upstream`.  It stays pristine — no infra to re-apply.
2. Rebase `base` onto the new `upstream` (`git rebase --onto upstream <old-upstream> base`,
   or `git branchless move`); resolve any infra-vs-upstream clashes once.
3. `git restack` (git-branchless) re-applies every `feature/*` onto the moved
   `base`; resolve real source conflicts (rerere replays them next time).
4. Rebuild `integration` (`git show meta:tools/reintegrate.sh | bash`);
   force-push `base`, `integration`, and the rewritten feature branches.

## Building

Build with the **top-level `make` wrapper** (repo root), inside the `devenv`
shell so the Qt5 toolchain and gcc are on `PATH`:

```bash
make            # build the interpreter (default target) → repo root
make rebuild    # CLEAN rebuild — REQUIRED after a branch switch / reintegrate
make run        # build + run (native Wayland, X11/XWayland fallback; QPA=xcb to force)
```

**Non-interactive / agent shells (e.g. Claude Code's Bash tool):** `direnv` only
auto-loads this repo's `devenv` on an *interactive* shell prompt, for the directory
the shell **started** in — it does **not** re-trigger on a `cd` inside a
non-interactive `bash -c`.  So a tool shell that started in a *sibling* repo (this
box's harness starts in `../RiscPc`) has that repo's `devenv`, not this one:
`qmake`/Qt are missing and `make`/`./run` fail with *"Could not find the Qt platform
plugin 'wayland'"*.  Load this repo's env explicitly instead:

```bash
direnv exec /home/msharman/Projects/rpcemu make          # or: make rebuild / make run
direnv exec /home/msharman/Projects/rpcemu ./installs/<name>/run
```

(Equivalently `devenv shell -- make` from the repo root.)  An interactive VS Code
terminal opened in this repo already has the env via direnv, so this only matters
for automated shells — the `run` script and `Makefile` deliberately stay clean and
assume the devenv is active, rather than re-bootstrapping it themselves.

**Do not run `qmake`/`make` directly in `src/qt5/`.**  The wrapper pins
**`QMAKE_CFLAGS+=-std=gnu17`**; without it, gcc 15 (whose C default is C23) fails
to compile upstream's hand-rolled `typedef int bool` in `hostfs.c`.  The wrapper
is the **only** supported entry point — the raw `src/qt5` build will not compile
here.  (This is exactly why the old "cd src/qt5 && qmake && make" instructions
kept failing.)

**Always `make rebuild` after switching branches or running `reintegrate.sh`.**
A `git checkout`/`merge` updates the *source* but not the *binary*, and often
leaves source mtimes untouched — so a plain `make` sees nothing to do and
silently keeps the **stale** binary (e.g. missing the very feature you just
switched to).  `rebuild` does `make clean` first, forcing a full recompile.

Targets: **`make`** = interpreter (`rpcemu-interpreter`, repo root);
**`make recompiler`** = dynarec (`rpcemu-recompiler`); `make clean`.

**Use the interpreter.**  The dynamic recompiler is unstable on this
setup — RISC OS throws spurious errors under it (e.g. "no such SWI") because
the dynarec mistranslates the instruction stream; the interpreter runs
clean and is also the more timing-accurate of the two.

### Building the RISC OS modules (`riscos-progs/`) with the DDE

The `make` wrapper above builds the **emulator**.  The RISC OS modules in
`riscos-progs/` (`EtherRPCEm`, `HostCmd`, `HostFS`, `SyncClock`, …) are a
separate build: they need Acorn's toolchain (`cc`/Norcroft, `objasm`, `cmhg`,
`Link`, driven by `amu`), which has no Linux port.  So we build them **inside**
an emulated guest and drive it from the host over the HostCmd socket:

```bash
# once per install: unpack a ROOL DDE zip into the guest (recovers RISC OS filetypes)
tools/dde/dde-setup.sh ~/path/to/'ROOL DDE31d (2024)(RISC OS Open).zip' installs/riscos-530

(cd installs/riscos-530 && ./run) &            # boot; creates hostcmd.sock
cp -a riscos-progs/EtherRPCEm installs/riscos-530/hostfs/Build/EtherRPCEm
tools/dde/dde-amu.sh installs/riscos-530 Build.EtherRPCEm    # runs the project's Makefile
cp installs/riscos-530/hostfs/Build/EtherRPCEm/EtherRPCEm,ffa installs/riscos-530/netroms/
```

`dde-amu.sh` runs `amu` on the project's own Makefile end to end — edit on the
host, build on the guest, read the result on the host.

- **You need ROOL DDE 30+** (DDE31d known good); it is commercial, supply your
  own copy.  The 1998 Acorn C/C++ in the RPCEmu starter pack **will not do** —
  its Norcroft is C89 and its stubs are 26-bit only, and RISC OS 5 is 32-bit.
- **Build on a RISC OS 5 install** (`installs/riscos-530`); it needs
  `poduleroms/hostcmd,ffa`.  RISC OS 3.7 cannot run DDE31 at all.
- **Wait for the desktop** before building — `cc` gets no application slot
  before then and fails with *"No writable memory at this address"*.
- **Never hand-run `cc` and let `amu` do the rest.**  It yields a
  byte-identical module, so it looks fine, but it is no longer a Makefile build
  and skips the step most likely to break.  If `cc` fails inside `amu`, it is an
  application-slot shortage: `dde-amu.sh` already issues `WimpSlot -min 1024k`
  in the **same** `OS_CLI` as `amu` (via an Obey file), which is the only way it
  sticks — every `rpcemu-run` command is its own `OS_CLI`.  Override with
  `DDE_WIMPSLOT=2048k` if a project needs more.

See **`docs/dde-build.md`** for the full detail and gotchas.

#### The built modules in `netroms/` are integration-only artifacts

`netroms/*.ffa` are **build artifacts, and only `integration` carries a current
one.**  Feature branches change `riscos-progs/` sources **only** — deliberately:
a binary cannot be composed by merging, so if two driver-fix branches each
shipped one they would conflict on it, and neither's binary would contain the
other's fix.

The consequence is a real trap: **`reintegrate.sh` resets to `base`, so it throws
away the last rebuild.**  After any reintegrate that changed a `riscos-progs/`
source, rebuild and re-commit **on `integration`**:

```bash
(cd installs/riscos-530 && ./run) &     # boot the build machine to the desktop
make riscos-modules                     # -> netroms/*.ffa
git commit netroms -m 'netroms: rebuild EtherRPCEm'
```

`make riscos-modules` builds **whatever branch is checked out** — run it on
`integration`, the only branch with all the source fixes.  On a feature branch it
will happily produce a module missing the *other* branches' fixes.

Nothing enforces any of this, so a stale `netroms/` binary is the failure mode to
watch for: the *sources* look fixed while the module RPCEmu actually loads is
not.  (It has already happened once — both EtherRPCEm driver fixes were
source-only, and the shipped module still had both bugs.)

`installs/<name>/netroms/` is seeded from `netroms/` by `tools/setup-install.sh`,
so an install made from a stale tree carries the stale module too.

## Testing

**Policy: ALL dev tooling lives in the `devenv` (`devenv.nix` on `base`) — do
not vendor a tool into the tree or provision it ad-hoc (`nix-shell -p …`) in a
test script.**  A test/dev dependency belongs in `devenv.nix`'s `packages` so
every branch — and every contributor, agent shell, and the `integration`
build — gets it reproducibly from one place, and it stays out of the
`git diff upstream feature/X` upstream diffs (like the rest of the base infra).
Current test tooling: **`criterion`** (C unit tests) and **`pytest`** (via the
`python3.withPackages` env, alongside `mcp`).

Test suites (each its own independent feature branch, composed into
`integration`; run from an integration checkout so the code under test is
present):

- **`tests/unit/`** (`feature/ide-tests`) — Criterion C unit tests. They
  `#include` a `src/*.c` directly to reach its `static` functions, stubbing
  the few hardware globals. Run: `tests/unit/run.sh`.
- **`tests/e2e/`** (`feature/e2e-tests`) — pytest end-to-end suite driving a
  guest over HostCmd + MCP. Run: `tests/e2e/run.sh`.

## Running

- Put a ROM in `roms/` — a single 4 MB `.rom` is a valid image on its own;
  RPCEmu concatenates everything in `roms/` alphabetically.
- `cmos.ram` (CMOS NVRAM) and `rpc.cfg` (GUI config) are **untracked and
  auto-generated** with sensible defaults if absent — they are local
  runtime state, not source.  `hd4.hdf` is a local hard-disc image.
- On a Wayland desktop, run the Qt5 binary with `QT_QPA_PLATFORM=xcb`
  (and ensure `libxcb-cursor0` is installed).
